# A股工作流程诊断报告

> 审计对象：docs/000_Ashare_workflow.md  
> 审计日期：2026-07-14  
> 审计方式：只读分析、现有产物核对、临时目录 dry-run 与有限公开行情验证

## 1. 总体结论

工作流的架构方向正确，主要文件和脚本能够局部产出结果，但规则口径、时点控制、状态迁移和关键风控尚未闭环。

当前系统更适合被定义为：

> 可运行的投资研究流程原型，而不是已经完成端到端验收的交易执行系统。

综合判断：

| 评估维度 | 结论 |
|---|---|
| 总体分层架构 | 合理 |
| 主文档内部一致性 | 不通过 |
| 主文档与个人体系、README、技能一致性 | 不通过 |
| 文件和脚本机械运行 | 部分通过 |
| 业务语义正确性 | 关键环节不通过 |
| Point-in-time 与防未来函数 | 不通过 |
| 买前、止损、组合风险控制 | 不通过 |
| 历史验证和审计复现 | 不通过 |
| 当前是否适合直接指导实盘 | 不建议 |

本报告将“跑通”区分为四个层次：

1. 脚本能启动并生成 CSV。
2. 上下游 schema、状态和数量可以闭合。
3. 结果符合文档定义及 point-in-time 原则。
4. 输入失败、数据过期或状态缺失时能够 fail closed。

当前不少环节通过第 1 层，部分通过第 2 层，但阶段三滚动更新、买入冻结、持仓止损、组合风险和回放验证未通过第 3、4 层。

## 3. 值得保留的设计

以下核心思路是正确的，不建议推倒重来：

1. 公司质量与证券估值分离，避免把“好公司”和“好价格”混为一谈。
2. 质量、估值、量价触发、买前闸门、成交、持仓监控分层。
3. worth_attention、boundary_pending、garbage 与 L1–L4 分开。
4. 先确定策略标签，再选择对应估值方法。
5. 已引入 valuation_reviewed_at、valuation_price_as_of、evidence_available_at 等时点字段，[§6.7](000_Ashare_workflow.md#L674)的方向正确。
6. 明确“候选不等于订单”，并设置买前闸门和成交回写。
7. 意识到复权价格和绝对止损价不能混用。
8. 已认识到用当前估值池做历史回放存在幸存者偏差。

问题不在总体架构，而在这些原则尚未被一致、可验证地落实到数据合同和脚本中。

## 4. 阻断级问题

### 4.1 唯一规则源实际上并不唯一

最明显的是估值范围：

- 主流程多处已规定 L1–L4 全量估值，[§6.1](000_Ashare_workflow.md#L431)和准入矩阵也覆盖 L1–L4。
- 同一文档的固定产物、烟蒂说明和执行步骤仍写 L1/L2。
- [README](../README.md#L12)及[估值技能](../.agents/skills/a-share-valuation-pool/SKILL.md#L8)仍限定 L1/L2。
- 实际名为 a_share_focus_watchlist_l1_l2_valuation.csv 的文件却包含全部 261 家 L1–L4 公司。

其他直接冲突包括：

- 路由表称“11项买前闸门”，正文实际是 13 项资格条件加 3 项当日事实，共 16 项。
- 工作流规定 100%–160% 总仓位，个人体系仍规定强市、震荡市、弱市分别为 75%–100%、45%–75%、15%–45%。
- 同时存在“一笔建满”“目标仓位 1/3”“三批买入”。
- 盈利减仓、趋势保护、杠杆、三个月锁定、左侧首笔 3%/5% 均存在两套口径。

如果两名执行者分别依照不同段落或技能，可以合法地产生不同结果。这是流程不可复现的根本问题。

### 4.2 Universe 不是“当前可投资证券名单”

当前 5,653 条 universe 中有 138 条名称为“-”的退市占位证券。抓取脚本只拒绝空名称，“-”会被接受，[检查逻辑](../scripts/fetch_a_share_universe.py#L142)存在缺口。

当前 universe 缺少：

- 上市、暂停、终止上市和退市整理状态。
- 是否当前可交易。
- 证券类型和生效区间。
- 公司与证券的多对多映射。
- 吸收合并、重新上市和代码迁移处理。
- universe 增删差异报告。

估值池脚本又不强制连接最新 universe，因此退市、失效或已移除证券可能继续留在 tiers、valuation 和 daily pool 中。

当前 universe 来源时间仍为 2026-05-11；本次 2026-07-14 刷新又因单一来源失败而整体中断。

### 4.3 质量审查虽然数量闭合，但研究证据未验收

当前 261 条 tier 的 evidence_sources 全部含有“模型既有知识判断，权威材料需后续刷新”，并没有直接权威来源链接。

因此：

- 结构化分层完成度：261/261。
- 能从产物证明完成权威材料复核：0/261。

当前 tiers 应被视为 provisional，而不是正式完成的 deep review。

质量定义本身也混入了时间和交易因素：

- [§5.8](000_Ashare_workflow.md#L384)声称只判断业务质量。
- L3/L4 条件却包含行业催化、右侧信号、周期拐点、催化清晰度。
- AI/半导体又允许“持久性较弱”的瓶颈成为 L1，与 L1 的持久护城河定义冲突。

建议 L1–L4 只表达业务质量；催化、证据成熟度、周期位置和买入状态全部另设字段。

### 4.4 质量队列和同行校准不能按设计运行

季度质量队列要求识别“较上次审查发生重大变化”，脚本却判断绝对水平，[脚本条件](../scripts/build_quarterly_quality_review_queue.py#L106)包括高毛利率、高研发率、高负债率等。

结果是 5,337 家 boundary 中约 70% 被重新拉入队列，违背“无硬触发不复核”，也失去人工可执行性。

全量重扫脚本读取不存在的 current_attention_class，而真实字段是 attention_class，[错误位置](../scripts/build_a_share_full_rescan_queue.py#L48)。实测全部 5,653 家被重建成未审查。

同行校准则存在更直接的断点：

- §0 路由没有同行校准任务。
- 主流程没有正式输入、输出和合并协议。
- 技能引用的三个脚本和 a_share_final_screening_results.csv 均不存在。
- ADR/CONTEXT 与主流程存在两个竞争性的 source of truth。

目前同行校准只能阅读历史叙事，不能重新运行。

### 4.5 估值结果存在循环论证和时点异常

261 条估值中约 134 条使用以下路径：

1. 先确定“低估、较低估、中性、高估”等档位。
2. 再按当前价格乘固定区间反推合理价。

这不是独立估值，而是用结论证明结论。部分记录甚至明确说明模型锚点与档位不符后，改按档位带换算。

当前至少 6 条“中性”记录的估值价格不在合理价区间内。

此外：

- 6 条记录使用了晚于 valuation_reviewed_at 才公开的证据，存在时点穿越。
- 3 条策略标签与实际估值方法不一致。
- 档位边界大量重叠，例如 12%、PEG 0.7/1.0/1.5/2.0、D类 60/80/100/120 均可同时落入两个档位，[估值表格](000_Ashare_workflow.md#L637)需要使用半开区间。
- 只要求 bull case，没有完整 bear/base/bull、概率、下行空间和赔率字段。
- 所谓 DCF 实际是“FCF收益率＋利润增长＋分红回购＋估值修复”，不是现金流折现，并可能重复计算同一份现金流。
- 没有估值最大有效期或价格变化触发。公司不发新报告时，股价大涨也可能继续沿用旧的“中性”估值。

合理价必须由利润、NAV、FCF、股息或情景假设独立计算，再由当前价格判定估值档位。

### 4.6 核心估值池可能使用旧质量状态

工作流声称分层变化后会自动重算准入资格，但脚本优先使用估值行内旧的 quality_tier，[实现位置](../scripts/build_a_share_core_valuation_pool.py#L84)与规范不一致。

最小复现显示：

- 公司已从当前 tier 文件移除，旧估值行为 L1＋中性，仍可被纳入 core。
- 当前 tier 已降为 L4，旧估值仍写 L1，仍按 L1 纳入。
- core_valuation_eligible=no 也不会阻止纳入。

核心池必须强制以内联的最新 universe、attention 和 tier 为权威输入；任何缺失、降级或版本不一致都应 fail closed。

### 4.7 财报滚动更新使用了错误的时间语义

工作流正确地区分了报告期和公开日期，但更新脚本比较的是 latest_report_date，即报告期末，而不是公告公开日期，[脚本位置](../scripts/build_report_update_queue.py#L105)。

典型漏报：

1. 6月30日结束的半年报在8月公告。
2. 公司7月完成估值复核。
3. 因为报告期末早于7月复核日，脚本认为没有新报告。
4. 实际上该报告在7月复核时尚不可见，8月公告后理应触发复核。

重大事件复核也只有文字规则，没有事件输入表、公告时间、来源、处理状态和调度入口。

预期闭环应为：

    公告或事件出现
      → review_pending
      → 冻结买入
      → express review
      → 解冻

目前该链路没有真正跑通。

### 4.8 复核冻结是 fail-open

更新队列缺失时，文档允许继续扫描；脚本也只提示“冻结未启用”，不会阻止候选生成。

冻结又只作用于 buy_candidate，[实现位置](../scripts/screen_daily_volume_price_signals.py#L559)，没有覆盖 signal_watch_only。但 L2 可接受较高估、L3 中性正是可能通过事件通道转为买入的对象。

当前队列与估值池重合 45 家；其中 8 家触发 signal_watch_only，8 家均未被冻结。

对于任何可能进入买入路径的状态，以下情况都应禁止生成可执行偏向：

- 队列缺失。
- 队列过期。
- 队列 as-of 日期不匹配。
- 公司处于 review_pending。

### 4.9 每日量价信号的文档和算法不一致

主要问题：

1. 文档定义“当日成交量 ÷ 前20日平均成交量”，脚本的 MA20 包含当日，[计算位置](../scripts/screen_daily_volume_price_signals.py#L231)。这会系统性压低量比，3/5日量比还会出现分子、分母重叠。
2. 文档要求 A 级有前高、关键均线、温和放量或平台确认；脚本却把任意 L1/L2 低估至中性的普通买入信号都标 A，[优先级实现](../scripts/screen_daily_volume_price_signals.py#L418)。
3. 脚本没有 D 级，L3/L4 等其他情况统一落到 C。
4. “连续上涨”用 close 大于 open，不是收盘高于前一日收盘。
5. 长上影极端放量仍可能由通用规则生成买入候选。
6. S级未计算相对强度，却直接输出正式 S。
7. 非交易日或数据滞后时不强制 trade_date 等于 as_of。
8. 市场状态只有沪深300与MA250，缺少个人体系规定的宽度、成交额、主线和持续期。
9. 市场状态未知时仍继续生成候选。
10. 行情失败可能只写 data_error，但进程退出码仍为 0，调度层无法判断运行失败。
11. 原始行情没有不可变快照，日后无法精确复现当日结果。

当前当日输出中，21个 A 级有18个不具备文档要求的 A 级形态，说明偏差已经实际发生。

### 4.10 收盘确认和买入时间窗互相冲突

工作流同时规定：

- 标准信号收盘后确认。
- 盘中信号必须等待收盘才正式成立，[收盘确认](000_Ashare_workflow.md#L1095)。
- 所有买入只能在14:40以后，[执行时间](000_Ashare_workflow.md#L1556)。

收盘确认发生在15:00之后，当日已无法成交。

若推迟到下一交易日14:40，又没有定义：

- 信号有效期。
- 次日跳空容忍度。
- 是否重新计算估值和止损距离。
- 是否重新检查公告及过度延伸。
- pretrade 是否过期。
- 次日跌停、涨停或停牌怎么办。

必须明确为“14:40盘中 provisional 方案”或“收盘确认、下一交易日完整重验证方案”，不能混用。

### 4.11 买前闸门 Happy Path 尚未验证

当前买前 CSV 有6条记录，全部是 off_system，没有一条 approved。

同时缺少字段级 validator，无法自动确认：

- 所有资格条件是否填写。
- 报价、信号、账户快照是否同日。
- 止损是否低于计划买价。
- 是否有足够现金或融资额度。
- 当前持仓与买后仓位。
- 交易单位、预计股数、费用和滑点。
- 停牌、涨跌停、一字板。
- approved decision 与 execution 是否唯一对应。
- approved 是否已经过期。

因此现在只能证明“体系外买入可以被记录”，不能证明“体系内合规买入流程可以跑通”。

### 4.12 持仓止损和组合风险属于实盘安全缺陷

#### 4.12.1 止损触发错误

文档要求盘中触及止损即清仓，不等收盘，[Tier-0规则](000_Ashare_workflow.md#L1385)。脚本却只比较收盘价，[止损实现](../scripts/scan_holdings_sell_signals.py#L268)没有读取当日最低价或实时价。

因此“盘中跌破止损、收盘收回”不会触发。

#### 4.12.2 position_status 未落实

文档对 qualified 和 pending_adjustment 规定了不同止损及锁定语义，却又承认脚本不读取该字段，依赖人工改写结果。

关键止损不能由脚本先判清仓、再由人工覆写。

#### 4.12.3 组合风险口径错误

- 权重使用持仓市值作分母，而不是账户净资产，[权重计算](../scripts/scan_holdings_sell_signals.py#L345)。
- 不直接使用账户快照里的净资产、总资产和现金。
- 使用 --symbols 扫描子集时，把子集当成整个账户。
- 仍保留已退役的25万元 build_amount。
- 不检查袖位、席位数、行业或产业链暴露、100%–160%总仓位、6%/8%止损网格。
- 持仓表本身没有 sleeve、industry、industry_chain 字段。
- 公司行动依赖人工调整，没有 corporate-action preflight，除权日可能误触止损。
- 没有 T+1可卖数量、跌停未成交、部分成交、挂单中等状态。

#### 4.12.4 仓位数学不闭合

四个袖位上限相加：

    45% + 30% + 36% + 18% = 129%

但总包络允许到160%，严格遵守袖位上限时不可能达到160%。

6%止损预算在129%仓位下对应平均止损距离约4.65%，并不是文档写的6%；160%仓位下更只有3.75%。[仓位规则](000_Ashare_workflow.md#L1292)需要重新计算。

### 4.13 历史回放不能验证整个工作流

当前 backtest_signal_replay.py 只是单日价格信号重放，不计算：

- 后续收益。
- 最大不利波动和最大有利波动。
- 假阳性率、漏报率。
- 交易成本和滑点。
- 相对基准收益。
- 组合回撤。
- 正式通过或失败标准。

仓库没有 point-in-time 的历史质量池、估值池和公告时间线，因此无法证明历史某一天实际能够看到哪些公司和证据。

[§12.5](000_Ashare_workflow.md#L1268)还规定漏掉历史大牛股后单向放宽规则，这很容易围绕已知样本过拟合。应改为预定义训练集、验证集、留出集或 walk-forward，并同时约束误报和回撤。

### 4.14 运行、日志与版本治理不足

- 没有统一 run_id 或 run manifest，输入文件可能来自不同日期却组合成“当日最终结果”。
- 固定 CSV 被覆盖，没有每次运行的不可变快照。
- 决策日志5,372行中存在731组相同 stage/run/code/type 的重复键，只有16条使用 supersedes_decision_id。
- 日志 helper 缺少幂等键、文件锁和原子事务。
- 部分批次只记录一条 BATCH 日志，不能追溯到每家公司。
- 脚本错误状态不总是映射为非零退出码。
- 没有 schema version、迁移方案、回滚规则和文档—代码阈值一致性测试。

## 7. 两种后续修改方案

### 7.1 最小改动方案

保留现有 CSV 和脚本结构，优先修复阻断问题：

1. 先在主工作流建立唯一口径表，明确其对个人体系、README、技能的优先级。
2. 统一 L1–L4、仓位、杠杆、分批、盈利减仓、趋势保护和左侧3%规则。
3. 修复 full-rescan 字段名和季度队列的 delta 判断。
4. 将报告触发改为 available_at 或 notice_date，增加最小事件 override CSV。
5. 核心池强制连接当前 universe、attention、tier；任一不一致即排除。
6. 禁止按当前价格反推合理价；增加 bear/base/bull、赔率和半开区间。
7. 修正日扫量比、A/B/C/D、交易日校验和未知市场状态。
8. 将冻结改为 fail closed，并覆盖 watch-only 和事件通道。
9. 明确定义“收盘确认、次日14:40完整重验证”。
10. 止损使用 low 或实时价，直接读取 position_status。
11. 风险计算读取同日账户快照，移除 build_amount，增加袖位和行业字段。
12. 增加统一只读 validator 和少量黄金样例测试。
13. 当前261家公司在权威证据刷新前标记为 provisional。
14. 将临时持仓状态和具体案例移出主规范。

这是最小范围内可以把系统提升到“可重复 dry-run、人工审核后使用”的方案。

### 7.2 最干净完整方案

建立正式的版本化状态链：

    security_master + company_mapping
      → attention_decision
      → peer_calibration
      → business_quality_assessment
      → strategy_thesis
      → valuation_assessment
      → valuation_validity
      → scan_candidate
      → review_blocked / pretrade_pending
      → approved / expired
      → execution / partial_fill
      → holding
      → sell_review
      → execution / cancelled

同时：

1. 所有产物增加 run_id、schema_version、effective_at、available_at、evidence_cutoff。
2. raw、normalized、derived 全部保留不可变快照，固定文件只作为 latest view。
3. 建立 disclosure/event timeline，统一处理预告、快报、正式报告和重大事项。
4. 独立拆出组合风险引擎，负责净资产、袖位、席位、行业链、止损网格、回撤和融资风险。
5. 建立结构化 pretrade/presell validator，支持过期、撤单、部分成交、T+1和涨跌停状态。
6. 决策日志使用稳定幂等键；公司级结论逐条记录，batch仅作汇总。
7. 建立 point-in-time 历史池和 walk-forward 验证集。
8. 重大规则变化必须经过 ADR、schema migration、回放门槛和版本发布。
9. 增加文档—脚本一致性测试，避免技能和阈值再次漂移。

这个方案更适合长期把项目发展成可审计、可复现的投资研究与决策系统。

## 8. 建议的验收标准

在修复后，至少满足以下条件才能称为“全链路跑通”：

1. universe、triage、tiers、valuation、pool 之间无重复、孤儿、失效证券或旧状态覆盖。
2. 所有证据满足 available_at 不晚于 decision_at。
3. 报告在复核后公告时必定进入更新队列。
4. 队列缺失、过期或异常时，所有潜在买入路径均被冻结。
5. 人工构造的1.8倍量比样例严格命中，低于阈值严格不命中。
6. 文档中的A/B/C/D案例与脚本输出完全一致。
7. 盘中最低价触及止损、收盘收回的案例仍触发Tier-0。
8. pending_adjustment 与 qualified 产生不同且符合定义的动作。
9. 单证券扫描不会改变全账户风险分母。
10. 存在至少一个 approved → execution → holding 的完整黄金样例。
11. 存在 partial_fill、cancelled、expired 异常路径样例。
12. 全流程共享同一 run_id、as-of、规则版本和输入文件哈希。
13. 任一关键输入缺失时脚本返回非零退出码，不生成可执行候选。
14. point-in-time回放同时报告命中率、误报率、MAE/MFE、成本、相对收益和回撤。
15. git status、schema validator、单元测试和黄金样例全部通过。

## 9. 最终诊断

当前工作流不是“思路错误”，而是已经进入需要做系统性收口的阶段：

- 上半段存在数据状态、证据和估值可复现性问题。
- 中间的财报或事件更新和买入冻结没有真正闭环。
- 下半段的止损和组合风险实现与文档不符，属于最高优先级。
- 缺少统一运行批次、验证器和历史验收，使现有产物只能证明“生成过”，不能证明“正确且可复现”。

在阻断问题修复前，建议将当前输出定位为：

> 研究线索和人工复核辅助，不是自动可执行的买卖指令。
