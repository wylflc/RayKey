# 工作流一致性审核（2026-09-14）

审核结论：**参数值基本对齐，执行行为仍有缺口**。确认 10 项待处理事项，其中 7 项优先影响回测或交易计划，3 项涉及跟踪、编排和阅读产物。最关键的差异是回测一档金额使用成交日净资产，而现行流程和每日扫描使用信号日净资产。当前扫描没有发现名单泄漏或持仓报价分歧；187 份公司 README 已出现可复现的展示漂移，不能将其等同于 187 家估值错误。

**OI-180：回测的档位基数晚了一天**

工作流 §9.3.1.1 要求 T 日收盘净资产确定一档，§9.3.2 末尾要求 T+1 调手数而档位金额不变。扫描器直接使用传入的信号日 NAV。回测在 `sig_day = prev_trading[day]` 后，先以 `prices[code][day]` 标记持仓，再以该净资产计算 `budget` 和 `sell_budget`。这属于明确的时点差异，不是参数数值不同。证据：[回测标价与预算](../../scripts/backtest_valuation_strategy.py#L1948)、[扫描档位](../../scripts/screen_daily_volume_price_signals.py#L849)。

反例：信号日净资产 100 万元，一档应固定为 5 万元；次日持仓涨价后净资产 101 万元，回测将一档改为 50,500 元。在 12 元成交价下，标准应买 4,100 股，回测买 4,200 股。已排除费用干扰。建议分开保存信号日档位 NAV 与执行日盯市/偿债 NAV，再依 §12 做同输入配对验证；不能从此反例推断历史收益变化的方向或大小。

**OI-181：扫描与跟踪对旧行情的处理不同**

`scan_one` 对取回序列直接计算指标并取末根；没有要求末根日期等于 `as_of`，`section93_execution_plan` 也没有按 `signal_state`、报价日期过滤。输入截止 09-11 的 60 根有效报价、请求 09-14，结果仍为 `ok` 并产生买单；跟踪器对同一输入返回当日收盘缺失。证据：[scan_one](../../scripts/screen_daily_volume_price_signals.py#L259)、[跟踪的当日匹配](../../scripts/track_holdings_daily.py#L112)。

另外，扫描 P/V 使用前复权序列的末根收盘。代码自己注明历史日期时该值未必等于当日未复权价，却没有实现其注释所称的“仅最新交易日可出计划”限制。腾讯补尾还会把未复权新行直接接到前复权旧序列，仅调整成交量比例，缺少跨除权价格归一化。本次未调用供应商验证历史端点的实际锚定方式，因此这两项作为同一修复范围的静态证据。建议显式区分交易报价、估值用未复权收盘、均线用复权序列，并核对日期与调整基准；旧价可用于标记存量市值，不能作为当日可交易证明。

**OI-182：关键前置条件没有统一阻断**

缺复核队列返回 `None` 后继续买入；缺分层表返回空战术阻断集合；缺持仓表返回空仓；缺三类表只打印警告；缺持仓侧带回退候选侧。队列读取也未核对 §7.1 要求的当日新鲜度。候选侧模型文件缺失时，带 `--nav` 的运行仍可能退出 0，并留下上一份买卖清单。证据：[各加载入口](../../scripts/screen_daily_volume_price_signals.py#L427)、[持仓加载](../../scripts/screen_daily_volume_price_signals.py#L694)、[主流程](../../scripts/screen_daily_volume_price_signals.py#L1419)。

反例分别复现“无队列仍写买单、退出 0”和“无模型带、退出 0、旧计划原样留下”。这不符合工作流 §14 的受影响结论停止原则。建议对执行模式建立必需输入校验；空仓应由有效的空持仓表表达，不能由缺文件推断。只取行情与正式出计划应有明确的不同完成状态。历史回放另用对应日期的输入，不能仅靠今天的文件存在就放行。

**OI-183：退出码有了，但发布顺序仍不安全**

主流程先写 `daily_buy_candidates.csv`、审计日志、买卖计划及冷却文件，最后才调用 `data_error_exit_code`。在 2 行中 1 行行情失败的反例里，退出码为 1，但已经发布另一只的 100 股买单，并写入剩余冷却 2 次。证据：[主流程最后的返回](../../scripts/screen_daily_volume_price_signals.py#L1470)。

建议先完成故障比例和必需输入检查，再在临时输出中形成整批结果，通过后统一发布，并附可校验的运行日期/成功状态。失败时不得推进冷却；保留旧结果用于审计时须使下游明确知道其不是当日有效计划。现有失败测试只验证返回码，覆盖不到这一副作用。

**OI-184：出名单与买入资格各走一套**

`members` 用在出名单卖出，却未用于构建 `eligible`。只要过期核心池仍带着该票且其走势、P/V 合格，就能买入。合成 `members=set()` 时仍产生 500 股买单；持有 1,000 股的同一标的可同时生成“出名单卖 500 股”和“买入 500 股”，强制退出不做净额抵消。证据：[出名单分支](../../scripts/screen_daily_volume_price_signals.py#L935)、[合格集](../../scripts/screen_daily_volume_price_signals.py#L988)。

当前真实 181 只核心池与 worth_attention 集合完全相等，故未发现本次扫描已发生此问题。建议买入、新仓换仓触发者都显式与当前名单求交集，并将出名单与当日卖出来源去重一并核查。

**OI-185：缺价持仓从总仓位计算中消失**

扫描 `stock_value` 对缺报价取 0；因此虽然卖出表提示持仓数据缺失，总仓位约束仍可能按“持仓为零”继续买入。合成例中有 10,000 股缺价持仓，系统计算原市值 0，并生成 5 万元新买单。回测则维护最后可得价格，并将不能成交与应计入存量市值分别处理。证据：[扫描仓位与比例减仓](../../scripts/screen_daily_volume_price_signals.py#L952)、[回测标价](../../scripts/backtest_valuation_strategy.py#L1948)、[回测仓位约束](../../scripts/backtest_valuation_strategy.py#L1416)。

建议保留带日期的估值市值并单独判断能否交易；若无法确定存量市值，则停止依赖剩余仓位额度的新增计划。受限状态还应核对账户现金、债务快照的日期，不能无限沿用任意旧快照。

**OI-186：冷却状态缺少成交对应关系**

买入兜底先执行 `lot_ratio_ready(...)`，随后才检查现金是否足够。一档 5 万元、一手 15 万元、可用资金为零，结果没有买单却记冷却 2 次；下一次资金 20 万元时仍跳过并减到 1 次。回测在 `amount <= 0` 时提前跳过，因此至少零资金边界也不同。证据：[扫描兜底](../../scripts/screen_daily_volume_price_signals.py#L1128)、[回测资金检查](../../scripts/backtest_valuation_strategy.py#L3343)。

更广的设计问题是：§9.3.3 明确在扫描时写状态，§11.5 实际成交回写没有对应的启动、撤销或部分成交处理。扫描次日未成交、用户未执行或同日净额对冲后零成交，都可能留下计划层冷却。**已向用户询问启动应按实际成交还是按计划；本次未收到裁定，保留为待确认。** 无资金即启动的反例已独立确认为缺陷。建议未来让实际成交记录携带原信号日/计划标识；启动时点裁定后，保持同日重跑幂等以及买卖分侧计数。

**OI-187：持仓报告仍保留平行判断和旧带回退**

对非金融企业，跟踪器的模型 P/V 不可得时会退到池中显示带的中值；模型被拒或加载不到，但旧池尚未物化时，扫描无 P/V，跟踪却能显示数值并标“持有”。反例为空模型、池带 160–200、现价 100，跟踪给出 P/V 0.56。另有 `pool_row is None` 即提示按出名单逐日清仓的逻辑；“不在物化池”和“不在 worth_attention”不等价。证据：[跟踪估值与名单提示](../../scripts/track_holdings_daily.py#L211)。

建议拒绝/缺失沿用统一模型解析结果，展示带只作展示；出名单提示读取三类表或共同决策结果。当前 8 只持仓有效模型正常，扫描与跟踪收盘、MA60 相等，P/V 仅有输出精度差异。

**OI-188：每日编排缺少发布前闭环**

§9.1 第 3 步已经调用会写买卖计划的扫描器，第 4 步才处理持仓公司行动，第 5 步又描述形成计划，未明确调整后重新生成。按文字顺序直接运行，除权日可能用旧股数、成本、止损锚先产生计划；回测在每日循环开始先应用公司行动。应将公司行动及持仓回写前置。

`daily_postclose.sbatch` 的 `evidence` 与 `scan` 是独立阶段，扫描阶段没有验证同日证据阶段已成功，也没有强制解决估值复核队列。价格背离检查先后运行两次，是因为第一次读取上一份候选快照；第二次才覆盖新候选，但它发生在计划和冷却已经写出之后。第二次命中会非零退出，却不能撤回前面的产物。证据：[编排脚本](../../scripts/slurm/daily_postclose.sbatch)、[价格背离的候选来源](../../scripts/check_report_day_price_divergence.py#L147)。

建议依赖顺序为：更新并核验同日证据、处理公司行动与账户、必要的估值重建、取得当日报价和初步合格集、完成事件/背离复核、正式生成并发布计划、最后渲染报告。任务仍可分 SLURM 阶段执行，但阶段间须传递成功状态和输入版本。09-14 日志已如实说明公告截止北京时间 15:10、行业巡检部分覆盖；尚不能把该结果理解为次日执行前全部事件均已复核。

**OI-189：README 不是最后一个下游产物**

`build_company_dossier_readmes.py --check` 退出 1，307 份中 187 份与当前结构化输入不一致。其中 172 份仅第八节“现价隐含了什么”漂移，另 15 份还存在其他段落差异；例如京东方 A、中芯国际仍显示空区间占位和 `model_unvaluable` 原始标记。

直接原因之一是 §6.7 在第 4 步渲染 README，而其第八节从核心池 CSV 读价格与日期；核心池直到第 6 步才重建。美的例：现页为 09-07 的 86.27 / P/V 1.470；当前渲染输入已是 09-09 的 86.02 / 1.465。中材国际同样是 09-07 / 09-09 / 每日扫描 09-14 三个快照。这里价格日期标注本身是必要信息，问题是宣称完整重建后仍不能通过自己的检查。

建议把依赖核心池的 README 渲染放到核心池物化后，并明确 README 现价是估值重建日快照还是每日收盘。若只保留重建日快照，应在页面直接指向每日扫描，避免重复维护“当前现价”。当前有值的池带上下沿与档案 CSV 对比未发现不一致。证据：[渲染所读价格](../../scripts/build_company_dossier_readmes.py#L144)、[重建链](../000_Ashare_workflow.md#L323)。

**冗余与维护建议**

- 交易判断分散在 1,569 行扫描器、5,045 行回测引擎和 532 行跟踪器中。常量同步只能查数值，不能查时点、缺数和状态副作用。建议先抽取名单资格、走势、止损、档位与股数预算的纯函数；回测保留撮合/记账，扫描保留数据与计划发布。先用上述反例保护行为，再逐段归并，避免一次重写整个引擎。
- 参数目前由规范表、`SEC93_*`、`BASE` 和部分硬编码测试共同维护，`BASE` 还夹有大量历史说明。可以建立明确的生产参数对象，由扫描和 BASE 组装读取，文档校验再检查该对象；历史依据留在回测日志。研究开关和退役实验并非都应删除，仍有复现用途。
- 存在误导性旧注释：执行计划函数仍写“125% 且弱势”、`--since` 帮助仍称读取决策日志、冷却帮助仍称共用、跟踪止损注释仍写已取消的建仓放弃规则。清理这些描述应与行为核验分开，不据旧注释改策略。
- 两次价格背离检查和扫描/跟踪重复拉同一持仓行情，是输入依赖未明确的结果。让它们共享本次不可变报价快照，可同时减少取数、价格时间差和重跑。不能直接删掉第二次检查，它目前补查新合格集。
- `unittest discover` 不会运行 `test_failure_semantics.py` 的自定义 CASES；本次首次发现 0 个测试后，已按脚本入口执行 9/9。应给仓库一个明确的轻量检查入口，避免把发现 0 个测试的 OK 当成覆盖。
